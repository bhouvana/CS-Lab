# SHA-256 From Scratch

**Educational implementation.** Not vetted, not hardened, not audited —
do not use this for anything that needs a real cryptographic library.
Use it to understand how SHA-256 works, not to secure anything.

## What is this?

SHA-256 (FIPS 180-4) implemented from scratch in C — no OpenSSL, no
libcrypto, not even a system hash function. Every round, rotation, and
padding rule is written out.

```bash
./sha256 "abc"
./sha256 --file some-file.txt
```

## Why does it matter?

SHA-256 secures a huge amount of real infrastructure (TLS certificates,
Git commit IDs, Bitcoin, password hashing building blocks). It's built
from a small number of simple bitwise operations (rotate, xor, and,
majority-vote) repeated 64 times per 512-bit block — seeing that in
~90 lines of straight-line C demystifies what's otherwise treated as
an opaque black box.

## Concept

```text
message
   |
   v
padding            (append 0x80, zeros, then the bit-length, to a 512-bit boundary)
   |
   v
512-bit blocks
   |
   v
message schedule   (expand 16 words to 64 via sigma-mixing)
   |
   v
64 compression rounds  (Ch, Maj, big-Sigma0/1, add into working state)
   |
   v
hash state         (8 x 32-bit words, updated after every block)
   |
   v
256-bit digest
```

## How it works

- **Incremental API** (`sha256_init`/`update`/`final`, mirroring
  OpenSSL's own shape): data is buffered until a full 64-byte block is
  available, then compressed immediately — so hashing a file streams
  it in fixed-size chunks rather than loading the whole thing into
  memory as one buffer for the hash function itself (the CLI still
  reads via `fread` in a loop; see `src/main.c`).
- **`sha256_final`** does the padding by hand (not by calling
  `update()` again) specifically to avoid double-counting the padding
  bytes into the message's recorded bit-length.
- **Message schedule**: the first 16 of the 64 32-bit words per block
  are the block itself (big-endian); the remaining 48 are generated by
  mixing earlier words with `small_sigma0`/`small_sigma1` — this is
  what makes every output bit depend on the whole block, not just 16
  words of it.

## Implementation

- `include/sha256.h` — public API.
- `src/sha256.c` — the whole algorithm: round constants, message
  schedule, compression function, padding.
- `src/main.c` — CLI.
- `src/bench.c` — the throughput experiment.
- `tests/test_sha256.c` — FIPS/NIST test vectors plus edge cases.

## Example

```text
$ ./sha256 ""
e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855

$ ./sha256 "abc"
ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad

$ ./sha256 "hello world"
b94d27b9934d3e08a52e52d7da7dabfac484efe37a5380ee9088f7ace2efcde9

$ ./sha256 --file src/sha256.c
d6c7883eb9f487f75cb7bbf47df0ed122e16dc86283b3ebef47b26aa1a64fc70
```

All three string examples were independently cross-checked against the
system's `sha256sum` while building this lab and matched exactly.

## Experiments

**How does hashing throughput scale with input size?** `src/bench.c`
hashes 1 KB, 1 MB, and 16 MB buffers, auto-repeating small ones until
50ms elapse (since `clock()`'s resolution can't time a 5-microsecond
hash directly) and reporting the per-hash average.

Real output from `make benchmark`:

```text
input     reps    ms/hash     MB/s
1 KB      10148   0.0049      207.8
1 MB      12      4.8333      216.9
16 MB     1       84.0000     199.7
```

## Results

Throughput holds steady around 200-220 MB/s across three orders of
magnitude of input size — expected, since SHA-256 does the same fixed
amount of work (64 rounds of simple integer ops) per 64-byte block
regardless of total message size; there's no algorithmic superlinear
cost here, only the linear per-block cost. (A production SHA-256, using
SIMD/hardware SHA extensions, would be several times faster — this is
a portable scalar C implementation with no such optimization.)

## What I learned

The empty-string and "abc" test vectors are ubiquitous, but writing
them from memory into a test is exactly the kind of place a
transcription typo hides: the empty-string digest I first hardcoded
was missing its last hex digit, so the *test* failed even though the
*implementation* was already correct. Cross-checking the CLI's actual
output against the system's `sha256sum` (a completely independent
implementation) was what confirmed which side had the bug.

## Limitations

- Educational implementation — no side-channel hardening, no
  constant-time guarantees beyond what falls out naturally from having
  no secret-dependent branches (see `security/constant-time` for that
  topic specifically), not fuzzed or professionally audited.
- No SHA-224/384/512 variants — this lab implements exactly one
  algorithm end to end rather than a family.
- No hardware acceleration (SHA-NI, ARMv8 crypto extensions) — pure
  portable C.

## Further experiments

- Implement SHA-224 (same algorithm, different IV and truncated
  output) and note how little code that adds.
- Compare throughput against `openssl sha256` on the same machine to
  quantify the hardware-acceleration gap.
- Feed the incremental API 1-byte-at-a-time updates and confirm the
  digest is unchanged (stresses the buffering logic harder than the
  existing uneven-chunk test).
